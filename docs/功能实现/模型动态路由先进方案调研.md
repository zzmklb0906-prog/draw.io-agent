# 模型动态路由先进方案调研

## 1. 结论

模型路由的目标不是选出“综合能力最强的 Top K”，而是对每次请求选择一个满足质量、能力和运行约束的最低成本模型。候选模型可以全部参与本地分析，但单次请求只执行一个主模型；候选列表只用于解释、评估或故障回退，不能代表多模型并行分析。

本项目当前存在两套路径：

- 生产路径仍由 `ModelRoutingService -> CompositeModelRouter` 的关键词启发式链路选择 Fast、Balanced 或 Reasoning。
- `RoutingContext -> Requirement -> Constraint Filter -> Dynamic Ranking -> Evaluation` 新链路仅运行在 Shadow 模式，推荐结果不会修改实际请求模型。
- Evaluation 中的 Top 3 只是遥测快照，不会调用三个模型，也不是运行时 Fallback。

因此，当前核心问题不是“遍历所有模型”，而是旧生产规则不鲁棒，以及新排序采用单一加权总分后可能在某些 Agent 需求底线下压制 Fast。

## 2. 当前实现的主要缺陷

### 2.1 旧生产路由不具备真正的语义能力

`SemanticVectorModelRouter` 实际为关键词子串和权重累加，没有 Embedding；`LlmClassifierModelRouter` 实际为字符长度与关键词分支，没有调用 SLM/LLM。否定、同义词、中英文混合、短文本复杂任务和长文本简单任务均容易误判。

### 2.2 Agent 固定底线覆盖当前任务

`AnalystAgentRequirementPolicy` 无条件提高 reasoning、instruction-following 和 structured-output 要求。简单标题修改进入 Analyst 后也可能被当作高要求结构化任务，使 Flash 能力匹配度下降，而成本权重只有 5%，最终被多款强模型挤出前列。

任务动作和工作流阶段应优先，Agent 角色只补充当前阶段确实需要的能力，不能给所有请求施加同一能力下限。

### 2.3 单一加权总分不是正确目标函数

能力、成本、上下文余量和确定性被压成一个总分，存在以下问题：

- 能力短板可以被其他维度平均掩盖。
- 成本只有 5%，不足以表达“简单任务优先使用便宜模型”的产品目标。
- 成本按当前候选的最大值、最小值归一化，新增极端价格模型会改变已有模型得分。
- 缺失定价被赋中性分，可能意外优待元数据不完整的模型。

应采用词典序约束：先满足硬约束和质量底线，再比较成本、延迟、可靠性。

### 2.4 显式覆盖与硬约束边界不完整

当前用户只要提供非空模型名即可直接覆盖。模型不存在、被禁用、缺少 Vision、Provider 未配置时，也可能一直执行到下游失败。正确规则应是“有效的显式覆盖绝对优先；无效覆盖明确失败”，不能静默改选，也不能绕过基本可执行性检查。

### 2.5 评估数据不足

核心 benchmark 只有 8 个案例，且多数 `preferredModel` 是规则标签，无法证明真实模型质量差。正式切流前需要针对所有候选模型收集实际输出质量、成本、TTFT、总延迟和失败率，并保留独立测试集。

## 3. 行业与研究方案

### 3.1 Amazon Bedrock Intelligent Prompt Routing

AWS 在同模型家族中预测候选模型对当前请求的响应质量，只有更强模型的预测质量收益超过配置阈值时才升级，否则使用成本更低的 fallback 模型。每次请求只转发给一个模型。

来源：<https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html>

可借鉴：质量差阈值、单模型执行、路由可追踪、定期用实际质量和成本重新评估。

### 3.2 Microsoft Foundry Model Router

Microsoft 使用专门训练的轻量路由模型分析完整请求，并提供 Cost、Balanced、Quality 三种运行模式。模型池先受合规和能力子集约束，再在子集中选一个模型。

来源：<https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/model-router-how-it-works>

可借鉴：Fast、Balanced、Reasoning 应表示不同的质量—成本策略，而不是 Top K 配额或强弱模型数量比例。

### 3.3 RouteLLM

RouteLLM 利用偏好数据学习强模型和弱模型之间的质量差，以阈值控制是否升级到强模型，并以单模型调用降低成本。

来源：<https://arxiv.org/abs/2406.18665>

适用时机：项目积累足够真实、经过评审的模型输出比较数据后。当前数据量不足，不应立即引入训练路由器。

### 3.4 UniRoute

UniRoute 将路由目标描述为从动态模型池中选择能够完成任务的最小可行模型，并研究新模型加入后不完全重训的路由方式。

来源：<https://arxiv.org/abs/2502.08773>

可借鉴：选择“最小充分模型”，而不是选择静态能力总分最高模型。

### 3.5 FrugalGPT 与模型级联

FrugalGPT 让廉价模型先生成，通过可靠性评分判断是否接受；不可靠时才调用下一层模型。

来源：<https://arxiv.org/abs/2305.05176>

适用范围：Draw.io XML、严格 JSON 等具有本地确定性校验器的任务。开放式分析任务难以可靠验证，首期不使用级联，避免双重成本和尾延迟。

### 3.6 Semantic Router

Semantic Router 使用向量编码匹配语义路由，可改善关键词规则对同义词、多语言和表达变化的脆弱性。

来源：<https://docs.aurelio.ai/semantic-router/user-guide/guides/semantic-router>

边界：Embedding 适合识别任务意图，不等价于预测某个模型能否高质量完成任务，不能替代能力约束和质量评估。

### 3.7 RouterBench 与 LLMRouterBench

RouterBench 提供超过 40 万条多模型结果；LLMRouterBench 2026 对 21 个数据集、33 个模型和多种路由方法进行统一评估。其结论包括：不少复杂方法与简单基线表现接近；扩大模型池存在边际收益递减；模型池质量和实际 workload 评估比盲目增加路由复杂度更重要。

来源：

- <https://arxiv.org/abs/2403.12031>
- <https://arxiv.org/abs/2601.07206>

可借鉴：首期采用可解释的约束式路由，先建立本项目数据与基线，再决定是否使用 Embedding、学习路由器或在线 Bandit。

## 4. 推荐目标策略

```text
有效显式覆盖
  → 当前任务、Agent、工作流阶段需求分析
  → enabled / provider / vision / context / output 硬约束
  → Fast-safe / Balanced-default / Reasoning-required 运行模式
  → 筛选满足关键能力底线的模型
  → 按预计成本、延迟、可靠性和稳定 ID 依次决胜
  → 单模型执行
```

核心不变量：

1. 有效显式覆盖优先；无效覆盖明确报错。
2. Vision、上下文和输出限制不能被软分数绕过。
3. 每次只执行一个主模型。
4. Fast 不依赖配额；只要满足当前质量底线，就凭成本自然胜出。
5. 无法确定任务或没有充分模型时向上升级，不向下冒险。
6. Top 3 只用于遥测；故障回退需要单独的可重试错误和 Provider 隔离策略。

## 5. 暂不采用

- 不引入向量数据库或新的 Embedding 依赖。
- 不训练 SLM/LLM 路由器。
- 不启用在线 Bandit 探索。
- 不并行调用 Top 3。
- 不对 Fast 设置人为流量配额。
- 不在开放式任务上启用多模型级联。

这些能力应在真实标注数据、稳定质量评估和线上流量规模证明现有策略不足后再增加。
